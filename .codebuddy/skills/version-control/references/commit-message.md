# 提交信息规范（中文 + 类型前缀）

## 格式

```
<type>(<模块>): <中文简述>

<正文（可选，说明为什么改、影响范围、注意事项）>

BREAKING CHANGE: <不兼容变更说明（仅在确有破坏性变更时）>
```

- 标题一行，建议不超过 50 个字符，结尾不加句号
- `<模块>` 使用业务模块名（如 `字典管理`、`厨房管理`、`外部授权`、`租户管理`）；跨模块时用 `/` 连接，如 `厨房管理/外部授权`
- 简述用动词开头：新增 / 修复 / 优化 / 调整 / 移除 / 重命名 / 提取 / 补充

## 类型前缀表

| 类型 | 含义 | 典型场景 | 版本影响 |
|------|------|---------|---------|
| `feat` | 新功能 | 新增页面、新增字段、新增业务能力 | MINOR |
| `fix` | 缺陷修复 | 修 bug、修样式错位、修数据展示错误 | PATCH |
| `refactor` | 重构 | 拆分组件、抽公共函数，行为不变 | 无 |
| `perf` | 性能优化 | 减少请求、虚拟滚动、缓存 | PATCH |
| `style` | 格式 / 样式 | 缩进、命名、CSS 调整，不影响逻辑 | 无 |
| `docs` | 文档 | README、注释、接口文档 | 无 |
| `chore` | 杂项 | 依赖升级、构建配置、忽略文件 | 无 |
| `test` | 测试 | 新增或修正测试 | 无 |
| `revert` | 回滚 | 撤销某次提交 | 视情况 |

## 生成规则

1. 先看改动性质，再选类型：**是否新增了用户可见能力**（feat）→ **是否修复了错误行为**（fix）→ 否则归入 refactor / style / chore。
2. 一个提交只做一件事。若改动同时包含新功能与修复，应向用户提议拆分为多次提交。
3. 简述必须描述**业务行为变化**，不写实现细节（反例：`fix: 修改 if 判断条件`）。
4. 不确定模块名或改动意图时，直接向用户提问，不要猜测后写入。
5. 生成 **2-3 个候选** 供用户选择，并说明差异，例如：
   - 侧重行为：`fix(外部授权): 仅待处理和已接受状态可撤回`
   - 侧重范围：`fix(厨房管理/外部授权): 限制撤回操作状态范围`

## 对照示例

| 改写前（旧风格） | 改写后（本规范） |
|-----------------|-----------------|
| 修复菜单管理，只能删除无子节点的节点 | `fix(菜单管理): 仅允许删除无子节点的节点` |
| 修改账号和名称的 正则表达式 | `fix(用户管理): 调整账号与名称校验正则` |
| 厨房管理，设备卡片，添加设备类型显示，并添加超长提示 | `feat(厨房管理): 设备卡片展示设备类型并支持超长提示` |
| 租户管理，管理员信息，添加非必填，可编辑。添加邮箱输入格式校验 | `feat(租户管理): 管理员信息改为选填可编辑并新增邮箱校验` |
| 优化 | `refactor(全局): 提取公共分页与表单工具函数` |

## 禁止事项

- 禁止使用 `update` / `fix bug` / `修改代码` 等无信息量的标题
- 禁止在标题中写"若干"、"一些"、"部分"等模糊词
- 提交信息最终文本必须由用户确认，禁止在未确认时直接提交
