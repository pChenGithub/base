# memory 体系结构规范

## 四部分结构

`memory/` 下分四部分，单向依赖：

```
② 项目描述（pro_<简称>/PROJECT.md 及 PROJECT_*.md）─┐
③ 用户画像（PROFILE.md 及 PROFILE_*.md）────────────┼─ 蒸馏 ──▶ ① 蒸馏记忆 MEMORY.md（每次对话必加载）
④ 工作日志（pro_<简称>/logs/）──────┘
```

| 部分 | 文件 | 本质 | 会话加载 |
|---|---|---|---|
| ① 蒸馏记忆 | `MEMORY.md` | AI 提炼的结论（派生品，由画像+项目+日志蒸馏） | **每次对话必加载** |
| ② 项目描述 | `pro_<简称>/PROJECT.md`（及扩展 `PROJECT_<主题>.md`） | 项目客观事实（真相源） | 按需读取 |
| ③ 用户画像 | `PROFILE.md`（**必备组件，项目公用，持续迭代**） | 用户特质（真相源） | 按需读取 |
| ④ 工作日志 | `pro_<简称>/logs/YYYY-MM-DD.md` | 工作过程记录（真相源） | 按需读取 |

## 目录布局

```
memory/
├── MEMORY.md                # ① 蒸馏记忆（会话注入入口）
├── PROFILE.md               # ③ 用户画像（必备组件，项目公用，持续迭代）
├── pro_ZYACS_SmartDC/       # ② 项目描述 + ④ 工作日志（每项目一个文件夹）
│   ├── PROJECT.md           # ② 项目描述（固定名，必含四要素）
│   ├── PROJECT_需求明细.md  # ② 的扩展主题文件（可选，主题后缀询问用户确定）
│   └── logs/                # ④ AI 工作日志
│       └── YYYY-MM-DD.md    # 每日一个文件
└── pro_其他项目/            # 多项目协同开发：可存在多个 pro_<简称>/ 文件夹
    ├── PROJECT.md
    └── logs/
        └── YYYY-MM-DD.md
```

**支持多项目**：一个项目对应一个 `pro_<简称>/` 文件夹，可存在多个，适应多项目协同开发情况。

**多项目规则（v0.13~v0.23 确立）：**

- 当前操作项目：AI 按工作区目录/项目特征自动推断；**memory/ 下仅一个项目文件夹时默认其为当前操作项目**（不反复询问）；多项目且无法从目录推断时**每次询问用户当前项目**，不擅自猜测（v0.15~v0.16 确认）
- MEMORY.md 蒸馏产物按项目分节组织（**公共节：体系规则/用户协作要点 + 每项目一节：定位/架构/关键约定**），画像与体系规则为公共节
- **不做停维护归档**：不考虑停止维护项目，无项目归档操作（`memory/archive/` 不建立，v0.14 取消 v0.13 归档方案）
- 完整合规检查仅用户明确要求时触发；**检查对象为全部 `pro_<简称>/` 文件夹**（逐项检查 PROJECT.md + logs/ 及格式边界，全部合规才交付，v0.17 确认）；画像更新仅用户明确要求时执行
- **版本冻结**：体系稳定后由用户明确宣布冻结 v1.0，AI 不主动提议冻结

## 命名规范（v0.14 确立）

| 文件类型 | 规则 | 示例 |
|---|---|---|
| 蒸馏记忆 | 英文固定名 | `MEMORY.md` |
| 项目文件夹 | `pro_<项目简称>/`（简称=项目名称缩略，创建/校验时必向用户确认，**必不为空、必不省略**） | `pro_ZYACS_SmartDC/` |
| 项目描述主文件 | 固定名 `PROJECT.md`（位于项目文件夹内） | `pro_ZYACS_SmartDC/PROJECT.md` |
| 用户画像主文件 | 英文固定名，**必不为空、必不省略**（记忆体系必备组件） | `PROFILE.md` |
| 项目描述扩展文件 | `PROJECT_<主题>.md`（位于项目文件夹内，主题后缀询问用户确定） | `pro_ZYACS_SmartDC/PROJECT_需求明细.md` |
| 用户画像扩展文件 | `PROFILE_<主题>.md`（后缀询问用户确定，**仅放用户特质**） | `PROFILE_技术偏好.md` |
| 工作日志 | `pro_<简称>/logs/YYYY-MM-DD.md` | `2026-09-01.md` |
| 元信息 | 注释式文本 | `- 更新日期: 2026-08-31` |

通用约束：

- 不使用数字编号前缀（已取消编号方案，靠文件名与内容区分）
- 文件名不含空格与 `\ / : * ? " < > |` 特殊字符
- **项目文件夹名（pro_<简称>）必不为空、必不省略**：创建/校验项目描述文件时必向用户确认项目名称并缩略为简称，禁止根目录下散落的 `PROJECT.md`
- **用户画像文件 `PROFILE.md` 必不为空、必不省略**：记忆体系必备组件，缺失即不合规，创建 memory 体系时必须包含
- 项目描述扩展文件命名 = `pro_<简称>/PROJECT_<主题>.md`，用户画像扩展文件 = `PROFILE_<主题>.md`；**主题后缀必须询问用户确定后创建**；主题为英文时单词**首字母大写组合、不用下划线分隔**（如 `AiCorrections`）
- 扩展文件与所属核心文件靠文件夹/前缀关联，并在 MEMORY.md 索引中登记
- 元信息统一用注释式文本（人类可读），不用 YAML frontmatter

## 各部分内容定义

### ① MEMORY.md（蒸馏记忆）

- **只由蒸馏产生**：AI 读取 ②③④ 后提炼，禁止 AI 在会话中直接向 MEMORY.md 追加新信息
- 头部必须包含：
  - `蒸馏时间: YYYY-MM-DD`
  - `依据文件: 参与蒸馏的素材清单（含 PROJECT_*/PROFILE_* 扩展文件）`
  - `状态: 需重新蒸馏 / 已同步`
- 主体结构：**公共节（体系规则 / 用户协作要点）+ 每项目一节（定位 / 架构 / 关键约定）**（多项目按项目分节，v0.14 修正）
- 只含精炼结论，不含冗余细节；细节保留在素材文件中
- **必加载机制**：通过桥接规则 `rules/memory_load.mdc`（确定名，其他写法不合规；或 `CODEBUDDY.md`）保证每次会话注入

### ② pro_<简称>/PROJECT.md（项目描述）

项目描述主文件为固定名 `PROJECT.md`，位于 `pro_<简称>/` 项目文件夹内；文件夹名带项目简称（`pro_<简称>/`），简称来自项目名称缩略，创建/校验前必向用户确认，**必不为空、必不省略**。

客观描述项目，不掺杂个人观点。**内容必须包含四部分：**

1. **项目概述**：定位、用途、主要功能
2. **项目技术栈**：语言、框架、编译环境、依赖库、版本约束
3. **项目架构**：模块划分与职责、目录结构、数据流、设计模式
4. **项目模块**：模块清单与职责，以及各模块的**详细需求/功能**

模块的详细需求/功能**视具体需求而定**：明细量大时可拆入扩展文件（`pro_<简称>/PROJECT_<主题>.md`，后缀询问用户确定）。

**沟通纠正类扩展文件（按需创建，非必备）**：沉淀 AI 在本项目被用户纠正/沟通达成的**业务理解认知**（每条含【场景】-【纠正】-【此后行为】），用于跨会话防再犯；典型命名 `PROJECT_AiCorrections.md`（后缀询问用户确定）。创建时机：① 同一类纠正反复出现（≥2 次，logs 流水不便检索）；② 一次性重大纠正（影响面广、跨会话必知）；③ 用户明确要求。**非必备组件**：零纠正或仅单次小澄清时不建（记 logs 即可）；通用用户特质归 PROFILE、体系规则归 SKILL/MEMORY、编码规范归 rules、业务机制本身归 PROJECT.md 数据流节。

### ③ PROFILE.md（用户画像）

**必备组件（硬性要求）**：必不为空、必不省略，缺失即不合规；创建 memory 体系时必须包含。头部含注释式元信息（`# 标题`、`- 更新日期`、`- 状态`）。

记录用户本人特质（四要素为**内容框架，软性**：有则记录、无则空缺，不强制每要素必填；v0.17 确认）：

- 思考链路：分析问题的方式、决策习惯、偏好顺序
- 处事习惯：工作方式、协作偏好、对 AI 的要求
- 性格：沟通风格、表达偏好
- 母语：主要使用语言

**用户画像扩展文件（`PROFILE_<主题>.md`，后缀询问用户确定）仅放用户特质**：如技术偏好细节、工作流程偏好等。坑点、编码规范、检查点等一律归 rules 或 skill，不得写入扩展文件。

### ④ pro_<简称>/logs/YYYY-MM-DD.md（AI 工作日志）

- 记录每次编码/会话的关键工作：做了什么、决策、踩坑、验证结果
- append-only：只在末尾追加，不修改、不删除历史条目
- 条目格式：`- [HH:MM] 主题：内容`（**统一条目格式**，不使用 `## 小节标题` 式组织；v0.14 确认）；`[HH:MM]` **取真实本地时间**——写条目前先取系统时间，**禁止按对话节奏估算**（v0.22 确认）
- **文件首行（v0.24 确立）**：`# YYYY-MM-DD 工作日志`；历史文件首行写法不一致者（如仅 `# 日期`、`# 日期 日志`）按 append-only 宽限保留，不迁移、不判不合规
- **历史日志宽限（v0.19 确认，v0.21 扩围）**：新格式生效前已存在的**历史写法**日志（小节式 `## 标题`、段落式 `**主题**：内容` 等任意旧写法），一律按 append-only 保留原样、**不迁移格式、不判不合规**；新格式生效后新建的日志严格按 `- [HH:MM] 主题：内容` 执行。各项目的体系启用日期记录在该项目 `pro_<简称>/logs/`，本规范不写死具体日期
- **迁移与宽限必须用户确认（v0.20 确立）**：迁移（移动 / 重命名 / 改写既有文件的位置或格式）与宽限（历史文件豁免格式要求）的**是否执行、对象范围、方式**，一律**先提案 → 用户确认 → 才执行**；提案须列明待迁移文件清单（原路径 → 目标路径）、方式（移动 / 复制 / 改写）、是否改动内容、宽限对象与理由；未获确认时保持原状；已确认宽限仅按确认范围适用，新增 / 扩大 / 收紧均需再次确认，不得跨项目自动推广；**执行后不记录**（不写项目日志、不登记 `CHANGELOG`，v0.26）
- 是蒸馏的重要输入（尤其踩坑与决策是蒸馏为 MEMORY 关键约定的来源）
- **日志归属规则（v0.23 修订，v0.29 收敛）**：日志只记**与具体项目相关**的工作 → 记入该项目 `pro_<简称>/logs/YYYY-MM-DD.md`；**体系维护类工作不记日志**（skill / rules 调整、记忆体系检查与维护、画像维护等——**其痕迹如何记录由对应 skill / rules 自身机制决定，不属本 skill 管理范围**）；难以归属的其它工作 → 记入当前操作项目 `logs/`，不单独设立公共日志目录
- **画像观察记录不写日志（v0.15 确认）**：观察到用户新特质时**直接丢弃、不自动记录**；等用户明确告知或要求更新画像时才写入 PROFILE

## 项目记忆迁移（v0.25 确立，经用户确认）

**范围**（项目级操作）：项目文件夹改名 / 简称变更、跨仓库或跨工作区搬迁、合并、拆分。

- **授权**：与存量迁移同一机制——先提案（清单 / 方式 / 是否改内容 / 理由）→ 用户确认 → 才执行；未获确认保持原状
- **旧记忆不动**：原项目记忆**任何文件**（`PROJECT.md` / `logs/` 等）**不改写、不移动、不重排**，仅作为蒸馏的**事实依据**；旧位置文件一律保留，删除 / 覆盖须单独确认
- **产物**：蒸馏后**严格按格式形成 `PROJECT.md`**（四要素 + 头部元信息齐全），不照搬旧文件；`MEMORY.md` 由蒸馏重建，不手工搬
- **记录**：迁移本身**不记录**（不写项目日志、不登记 `CHANGELOG`，v0.26）
- **停维护项目**：不归档、不删除、不迁移
- 迁移后一致性：`MEMORY.md` 依据清单与项目节标题由蒸馏同步；其它文件中指向旧路径的引用一并核对

## 数据流与蒸馏规则

1. 新信息先写入对应素材（②③④），AI 不得直接改 MEMORY.md 来"记住"新信息
2. 素材中**关键内容**（定位/技术栈/架构/关键约定/协作要点等）实质变化 → **实时蒸馏刷新 MEMORY.md**（v0.18）；一般性变更（如常规工作日志追加）→ 标记 `⚠ 需重新蒸馏`
3. 蒸馏操作：读取全部相关素材 → 去重/压缩/提炼 → 刷新 MEMORY.md → 清除标记
4. 蒸馏触发：**重要信息实时蒸馏（v0.18 确认）**——项目描述/用户画像中关键内容实质变化时立即执行，不等待用户要求；常规工作日志追加不单独触发蒸馏（随下次蒸馏一并纳入）。**维护例外（v0.16）**：版本升级 / 规则修订 / 检查修正等体系维护流程完成后自动刷新 MEMORY.md（保证体系自身信息不滞后）

## 一致性原则

- 素材（②③④）是唯一真相源，MEMORY.md 永远可从素材重建
- 信息冲突时以素材最新内容为准，并重新蒸馏
- 不删除素材历史（保留演化痕迹），只更新内容
