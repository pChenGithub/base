# Rules Code Mgr — 编码类 rules 生成器

## Overview

本 skill 指导 AI 创建、修改、编码 **编码类 rules 文件**（CodeBuddy `.mdc` 规则，位于 `.codebuddy/rules/`）。核心三要素：

1. **文件命名规范**：固定前缀 `code`、按语言分文件、跨语言通用主题独立文件，保证可检索、可排序
2. **内容必须单元**：编程语言、语言版本特性（不强制指定版本，仅按需记录版本差异）、注释风格、禁止项、正向示例、反向示例
3. **个性化扩展挂载点**：每个 rules 预留可自由扩展的模块化单元

> 范围界定：本 skill 只管**编码类型**的 rules（如代码风格、语言规范、禁止项、示例）。**不管理** memory 记忆体系（归 `init-mem`）、rules 加载桥接（`rules/memory_load.mdc`，归官方机制）。

## 触发条件（强制：先加载对应 skill，再动手）

修改下列对象前**必须先加载**对应 skill，禁止凭“改动很小 / 已知内容”直接编辑；**脚本通过不等于流程完成**。

| 变更对象 | 必须先加载 | 说明 |
|---|---|---|
| `.codebuddy/rules/**`（`.mdc`） | `rules-code-mgr` | 编码规则的新增 / 修改 / 去重 / 客观化 |
| `.codebuddy/memory/**`（`PROJECT.md` / `PROFILE.md` / `MEMORY.md` / `logs/`） | `init-mem` | 记忆蒸馏、画像与项目描述维护 |
| `PROJECT.md` 中的需求与模块功能 | `req-check` | 需求完整性、模块职责检查 |
| 外部协议归档（HTTP / MQTT / 自定义帧等） | `proto-archive` | 请求方式 / 发送内容 / 响应内容三要素 |
| `.codebuddy/skills/**` | 该 skill 自身 | 按其 `SKILL.md` 流程执行，不改动其必备结构 |

**判定顺序**：先确认“要改什么对象”，再加载对应 skill，最后才进入编辑；改前自检必须包含这一项。

## 工作流决策

开始前先判定任务类型：

- **创建新规则** → 按【Step 0 前置盘点】→【Step 1 拆分与命名】→【Step 2 必备单元】→【Step 3 个性化挂载点】→【Step 4 写入与验证】
- **追加单条规范（目标文件已存在）** → 直接并入现有文件对应小节，按【Step 5 修改流程】
- **修改现有规则** → 按【Step 5 修改流程】（先读现有文件 → 定位单元 → 定向替换 → 校验）
- **编码（规范化）现有规则** → 按【Step 6 编码流程】（将非规范/散落规则纳入命名规范、补齐必备单元）
- **发现语言覆盖缺口（项目使用某语言但 rules 无对应规范）** → 按【Step 7 语言覆盖度检查】提示新建并给出建议（**不擅自新建**）

## Step 0 前置盘点（创建/追加必做）

创建新规则或追加规范前，**必须先盘点** `.codebuddy/rules/` 已有文件：

1. **列出** `.codebuddy/rules/` 全部规则文件
2. **查重**：判断本次需求是否命中已有文件（同语言或同主题）
3. **判定归属**：
   - 已存在对应语言文件 → **并入现有文件**（不新建），按 Step 5 追加小节
   - 已存在对应通用主题文件 → 追加到该通用文件对应小节
   - 不存在对应文件 → 进入 Step 1 新建文件

### Step 0.1 先判「这条内容是不是编码规范」

Step 0 的"归属"解决**落到哪个 rules 文件**；本节解决**是否该落到 rules**。新增条文前先用三条测试：

| 测试 | 判为**编码规范**（入 `rules/`） | 判为**非编码规范**（不入 `rules/`） |
|---|---|---|
| ① **脱离设计稿是否仍成立**（把设计源换成任意 UI，这条还需不需要） | 需要（任何同类工程都适用） | 只在"还原这一份设计"时才有意义 |
| ② **违反后果** | **功能错 / 崩溃 / 不可维护**（点了没反应、内存泄漏、依赖倒置） | **与设计不符**（颜色差 1px、圆角没做、渐变近似） |
| ③ **修法触碰面** | 只碰语言 / 框架 API 用法（事件、句柄、生命周期、指针） | 必须改采集器 / 校验脚本 / 设计资料 / 交付流程 |

- **三条全中才入 `rules/`**；只中部分 → 拆开写：**纪律进 rules，流程与判据进 skill**
- **内容客观性（硬性，独立于三条测试）**：编码规范只做**客观描述**，不得绑定具体项目或具体业务——条文与示例中禁止出现项目名 / 产品名 / 业务模块名（如 `scbox`）、业务对象（继电器 / 电表 / 档位 / 告警等）、设备型号、项目全局变量、项目绝对路径；示例一律用通用或占位命名（`module_*`、`module_poll_ms`、`<语义>`）。项目事实（模块/业务/路径）写 `PROJECT.md`，不写进 `rules/`
- **通用规范必须抽象（硬性，仅 `code_general` 及其分片）**：通用规范是与具体语言、具体项目无关的抽象约定——**禁止**出现任何语言的代码块、语法、API、类型、语言专属标识符（`#define`、`malloc`、`cJSON`、函数内 `static` 变量等），**禁止**出现项目名 / 业务对象 / 设备型号；示例只能用“判定要素 + 正确做法 / 错误做法 + 合规改写”的抽象描述。语言专属条款一律下沉到 `code_<语言>.mdc`（无对应语言文件时先提示新建），项目客观事实写 `PROJECT.md`
- **落点对照**：

| 内容性质 | 落点 |
|---|---|
| 编码规范（语言 / 框架用法、禁止项、实现纪律） | `rules/code_<语言>.mdc`（同语言不重复；仅跨语言通用主题才独立成文件） |
| 设计实现规范（还原方法 / 采集口径 / 校验清单 / 工具链） | `skills/design-to-ui/references/` |
| 项目客观事实（定位 / 技术栈 / 架构 / 模块 / 关键约定） | `.codebuddy/memory/pro_<简称>/PROJECT.md` |
| 用户特质 | `.codebuddy/memory/PROFILE.md` |
| 设计未定义项的处理决定（如"开关断电态颜色取 #FFFFFF 40%"） | 用户确认后记 `PROJECT.md`（不是 `rules/`） |

- **禁止两处维护**：同一纪律只在一处写成条文，另一处写「判据 + 指针」（实测：`skills/design-to-ui` 与 `rules/code_lvgl.mdc` 曾同时写"主题默认样式"的修法，已收敛为 rules 单源）
- **易误判示例**：

| 内容 | 判定（依据） | 落点 |
|---|---|---|
| 控件取槽位的句柄必须与回调挂载对象一致 | 编码规范（① 是 / ② 功能错——点击失效 / ③ 只碰事件与句柄） | `rules/code_lvgl.mdc` 扩展 9 |
| `vector` 节点圆角须从 `fillGeometry` 路径反算 | 设计实现规范（① 否：脱离该设计源即无意义） | `skills/design-to-ui` |
| 内置控件做不出设计几何 → 须手写控件 | **拆开**：判据（库能否表达设计几何）留 skill；手写控件的实现纪律入 rules | skill + `rules/code_lvgl.mdc` 扩展 9 |

## Step 1 拆分决策与文件命名规范

### 1.1 拆分决策规则

编码类 rules 按以下规则决定文件粒度：

| 场景 | 拆分方式 | 示例文件 |
|------|----------|----------|
| 同一语言的多主题规范 | **合并为一个文件**（一个语言一个文件） | `code_cpp.mdc`（含 C++ 的版本特性/注释/禁止项/示例） |
| 跨语言通用的主题 | **独立成文件**（如注释风格、命名约定） | `code_comment.mdc`、`code_naming.mdc` |
| **精炼后仍超注入上限（8000 字符）** | **按主题新建补充文件**：主文件留必备单元与索引，明细移入补充文件 | `code_c.mdc` + `code_c_example.mdc` |

- 一个语言一个文件，不按主题拆散同一语言；**唯一例外**：精炼到极限仍超 8000 字符（见下条）
- **长度上限（硬性）**：always-apply 规则注入时**单文件正文上限 8000 字符**，超出部分被平台截断（末尾出现 `[... rule truncated at 8000 chars]`），且**默认裁掉文件尾部**——禁止项、示例等关键内容最易丢失，而截断不报错
- **超限处理顺序**：① 先精炼措辞（见 Step 5 第 7 条，**不得丢信息**）→ ② 仍超限则按主题新建补充文件，主文件顶部列出分片索引
- 拆分出的每个文件都**必须**独立声明 `alwaysApply: true`，否则仍会退化为按需加载
- **拆分细则（硬性）**：
  - 命名：`code_<语言>_<主题>.mdc`，主题词小写下划线（`example` / `state` / `pattern` / `api`）
  - 必备单元：拆分文件仍须六单元齐全，但内容可用**一行指针**指向主文件（如「注释风格」节下写「见 `code_c.mdc`」），避免重复正文
  - 主文件索引：正文首个二级标题前加一行 `> 分片：code_c.mdc（条文）/ code_c_example.mdc（示例）`
  - 数量上限：单语言分片 ≤3 个；超 3 片说明内容该重构，须回头精炼合并，不得继续拆
  - 长度检查：每片独立计算并各自通过 `list_rules.sh` 长度检查
- 除上述长度例外外，只有跨语言通用的规范才独立成文件
- 语言文件与通用文件内容重叠时，通用文件放"通则"，语言文件放"特例"并互相引用

### 1.2 命名格式

```
.codebuddy/rules/code_<语言或通用主题>.mdc
```

| 要素 | 规范 | 示例 |
|------|------|------|
| 前缀 | 固定 `code`，编码类统一，无序号 | `code_` |
| 主体 | 语言名（cpp/c/python）或通用主题（comment/naming） | `code_cpp.mdc`、`code_comment.mdc` |
| 后缀 | `.mdc` | - |

**命名硬性要求：**
- 所有编码类 rules 以固定前缀 `code_` 开头（**不使用序号**），便于 `ls`/搜索一次性检索
- 主体小写 + 下划线，单词式，表意清晰
- 禁止使用含空格、中文、大写驼峰的文件名
- 记忆加载桥接 `memory_load.mdc` 保留原名，不属于编码类（本 skill 不管理）

### 1.3 文件名确定流程

文件名由"归属判定 → 查重 → 主体词定名"三步推导（不是凭空取名）：

**Step A 判定归属类型**（决定主体词是语言名还是主题词）：
- 规则只适用于**单一语言** → 语言文件，主体 = 语言名
- 规则适用于**多种/所有语言** → 通用主题文件，主体 = 通用主题词

**Step B 查重**（结合 Step 0 盘点）：
- 已有同语言文件（如 `code_cpp.mdc`）→ **并入现有文件**，文件名不变，不新建
- 已有同主题文件（如 `code_comment.mdc`）→ 并入
- 无对应文件 → 新建，进入 Step C

**Step C 生成文件名并校验**：
- 格式 `code_<主体>.mdc`；主体词小写 + 下划线
- 语言名用约定俗成缩写（`c`/`cpp`/`python`）；通用主题词用表意清晰的名词（`comment`/`naming`/`error_handling`）
- 校验：无空格/中文/大写驼峰/序号；主体词不与语言名混淆

| 需求 | 判定 | 文件名 |
|------|------|--------|
| C++ 编码规范 | 单语言 → `cpp` | `code_cpp.mdc` |
| 所有语言注释规范 | 跨语言 → `comment` | `code_comment.mdc` |
| C++ 禁止裸指针 | 单语言 + 已有文件 | **并入** `code_cpp.mdc`，不新建 |

## Step 2 内容必须单元

每个编码类 rules 文件**必须**包含以下单元（缺失即为不合规）：

### 2.1 frontmatter（必填）

```yaml
---
description: 一句话说明规则适用范围与触发场景
globs:            # 适用的文件匹配模式，不限定则省略
---
```

### 2.2 正文必备单元

按顺序组织：

| 单元 | 内容 | 必填 |
|------|------|------|
| 适用范围 | 适用的语言/项目/文件类型 | 是 |
| 编程语言 | 目标语言（如 C++ / Python） | 是 |
| 语言版本特性 | 不强制指定版本；仅记录影响编码的版本差异，AI 已知的通用特性不赘述 | 否（按需） |
| 注释风格 | 注释的格式要求（文件头/函数头/行内，语言/中文） | 是 |
| 禁止项 | 明确不允许的行为/写法（负面约束） | 是 |
| 正向示例 | 符合规范的代码示例（`// 正确`） | 是 |
| 反向示例 | 违反规范的代码示例（`// 错误`） | 是 |
| 个性化挂载点 | 见 Step 3 | 是 |

- **示例自遵守（硬性）**：示例是规范的可执行样板，必须自身完全合规——命名风格与段数、客观性、格式均须满足本文件与 `code_general.mdc`；反例必须显式标注“错误”并给出合规改写。禁止“正例违反本规范其它条款”，也禁止反例顺带引入无关违规（反例只应违反它要说明的那一条）

## Step 3 个性化扩展挂载点

每个 rules 文件尾部预留一个**可自由扩展的模块化单元**，供后续按项目/用户习惯追加内容：

```markdown
## 个性化扩展

> 本单元为扩展挂载点：可根据项目/用户需要自由追加模块化小节，不破坏既有结构。
> 追加时保持小节独立、命名清晰、编号递增（## 个性化扩展 1、## 个性化扩展 2 …）。

### 个性化扩展 1
<!-- 追加内容：例如项目专属命名约定、团队特定规范、工具链约定等 -->
```

**规则：**
- 挂载点必须存在且格式固定（保留引导注释）
- 追加内容不得改动前面的必备单元；新增小节编号递增
- 若无扩展内容，保留空挂载点即可

## Step 4 创建流程（完整示例）

**内容基底**：规范条目以**通用最佳实践**为基底（如 Google C++ Style 精简版等），按项目实际情况裁剪；用户明确口述强调的规范优先、必须收录。

**写入方式**：直接按流程生成完整 `.mdc` 并落盘（无需先征求确认），结果供用户检查。

以"创建 C++ 编码规则"为例：

```text
code_cpp.mdc
```

```markdown
---
description: C++ 编码规范规则：语言版本特性、注释风格、禁止项与正反示例
globs: "**/*.{cpp,h,hpp,cc}"
---

# C++ 编码规范

## 适用范围

适用于本项目所有 C++ 源码（.cpp/.h/.hpp/.cc）。

## 编程语言

- 语言：C++
- 语言版本特性：项目编译选项 `-std=c++0x`（C++11）；C++11 通用特性（智能指针/auto/lambda）AI 已知，不赘述

## 注释风格

- 文件头：标明文件用途、作者、创建日期
- 函数头：`/** @brief 功能说明 @param 入参 @return 返回值 */`
- 行内注释：中文，`//` 单行，解释"为什么"而非"是什么"

## 禁止项

- 禁止使用 `using namespace std;`（全局污染）
- 禁止在头文件中定义非 inline 全局对象
- 禁止魔法数字裸用

## 正向示例

```cpp
// 正确：局部使用 using 声明 + 具名常量
void openDoor(int doorId) {
    const int kMaxDoors = 8;
    if (doorId >= 0 && doorId < kMaxDoors) {
        relayOn(doorId);
    }
}
```

## 反向示例

```cpp
// 错误：using namespace + 魔法数字
using namespace std;
void openDoor(int a) {
    if (a >= 0 && a < 8) { relayOn(a); }
}
```

## 个性化扩展

> 本单元为扩展挂载点：可根据项目/用户需要自由追加模块化小节，不破坏既有结构。
> 追加时保持小节独立、命名清晰、编号递增（## 个性化扩展 1、## 个性化扩展 2 …）。

### 个性化扩展 1
<!-- 追加内容：例如本项目（ZYACS_Dctr_328）约定：底层 C 实现 + 上层 C++ 封装，extern "C" 混编 -->
```

**创建完成后：** 运行 `scripts/list_rules.sh` 验证命名与结构合规，并按 **Step 8** 核对字符数、做一次精炼评估。

## Step 5 修改流程

1. **先读**：读取目标 rules 完整内容（不要凭记忆猜测）
2. **定位**：确定要改的单元（必备单元 or 个性化扩展）
3. **定向替换**：用 `replace_in_file` 精确替换目标单元，保持其余结构不动
4. **校验**：确认必备单元仍在、`code_` 前缀与文件主体未变、示例与正文一致，且**示例自身合规**（命名 / 段数 / 客观性），反例只违反其说明的那一条
5. **改后强制校验（脚本）**：每次修改规范后**必须**运行 `bash scripts/list_rules.sh`（检查命名 / frontmatter / 必备单元 / 客观性 / 同文件重复条文 / 长度）；存在不合规项时先修正再重跑，**全部通过才算完成**；报告结果时须附校验输出（长度监控与精炼评估见 **Step 8**，脚本通过不等于已精炼）
6. **描述精确性校验（必做）**：frontmatter `description` 必须与正文一致——用一句话覆盖“适用对象 + 核心约束 + 关键差异”，不得遗漏本文件主打单元、不得写入正文没有的主题、不得空话（“很重要 / 需要注意 / 尽量”之类）、不得堆砌文件名；脚本对超长（>120 字符）给出提示，须人工复核
7. **冗余检查与精炼（必做）**：
   - **信息完整性优先（硬性）**：压缩只作用于**措辞**，不作用于**信息**。判定口径、例外、禁止项、关键示例一律不得因压缩而丢失；描述必须全面完整，能压的只有表达冗余。**宁可超长走拆分，也不得靠删条款瘦身**
   - **冗余判定**：同文件重复条文 / 示例重复正文判断；跨文件同一纪律重复（另一处应只留「判据 + 指针」）；过程叙述（历史、背景、讨论、变更记录）；重复解释与形容词堆砌
   - **精炼手法**：同义条文合并为一条；示例只保留**最小可判定片段**（判定要素齐全即可）；长句拆为“判定 + 例外”；删去模糊限定词（尽量 / 建议 / 注意）；整段说明改表格或短句
   - **精炼约束**：不得改变判定口径与例外；精炼后重跑第 5 步脚本，并复核第 6 步描述仍与正文一致；**逐条核对信息是否仍在**（不是只看字符数下降）
   - **长度预算**：always-apply 规则单文件（含 frontmatter）≤8000 字符，每次修改后核对；超限按 1.1 的超限处理顺序执行（精炼 → 拆分），禁止以截断方式"达标"

**追加单条规范（并入现有文件）**：经 Step 0 判定目标文件已存在时，将新规范写入对应主题小节——新增禁止项/示例则追加进对应列表；新增主题则新增小节并保持单元顺序；不新建文件。

## Step 6 编码流程（规范化既有规则）

1. **盘点**：列出 `.codebuddy/rules/` 下全部文件，识别命名不合规（缺 `code_` 前缀、非规范命名）的文件
2. **重命名**：按 Step 1 规范统一（编码类加 `code_` 前缀；同语言拆散文件先按 1.1 合并；保持原内容）
3. **补齐**：检查每个文件必备单元，缺失的按 Step 2 补齐；已有内容不重复
4. **挂载点**：确保尾部存在个性化扩展挂载点
5. **验证**：运行 `scripts/list_rules.sh` 检查
6. **登记**：在变更说明中列出 文件 → 变更项

## Step 7 语言覆盖度检查（主动提示）

在编码、改码、评审、接手项目等任务中，若识别出项目实际使用的编码语言，须核对其在 `.codebuddy/rules/` 是否有对应的语言规范，避免"无规范可依"。

**1. 识别项目语言**：按源码扩展名与构建/工程文件判定（`*.c/*.h`→C，`*.cpp/*.cc/*.hpp`→C++，`*.py`→Python，`*.js/*.ts`→JS/TS，`*.java`→Java，`*.go`→Go，`*.rs`→Rust，`*.sh`→Shell；`CMakeLists.txt`/`*.pro`/`Makefile` 等仅作辅助，不单独作为语言依据）。

- **判定范围**：只统计**项目自研源码**（含构建脚本）；**排除第三方/依赖目录**（如 `base/` 或 `third_party/`、`vendor/` 下的库自带脚本），避免把依赖包里的 `.py`/`.sh` 误判为项目语言而产生误报
- **证据要求**：提示缺口时须给出依据（命中的扩展名与所在目录），便于用户核对

**2. 期望文件名对照**（主体词取约定俗成缩写，命名规则详见 `references/naming_convention.md`）：

| 语言 | 期望文件 |
|------|----------|
| C | `code_c.mdc` |
| C++ | `code_cpp.mdc` |
| Python | `code_python.mdc` |
| Shell/Bash | `code_shell.mdc` |
| JavaScript / TypeScript | `code_js.mdc` / `code_ts.mdc` |
| Java | `code_java.mdc` |
| Go | `code_go.mdc` |
| Rust | `code_rust.mdc` |
| 其他语言 | `code_<语言缩写>.mdc` |

**3. 判定与处理**：
- 已有对应文件 → 无缺口，不提示
- 无对应文件 → **缺口**：**不擅自新建**，向用户提示并给出建议；用户确认后按 Step 1~4 创建
- 只缺"跨语言通用主题"（如注释风格）时不单独报缺口，作为可选建议附带提出

**4. 提示模板**（缺口时一次列清，避免反复打断）：

```text
发现项目使用 <语言>（依据：<源码扩展名 / 工程文件>），但 .codebuddy/rules/ 下没有对应的编码规范文件。
建议新建 <期望文件名>，按本 skill 必备单元组织：
- frontmatter：description + globs（如 "**/*.{<扩展名>}"）
- 正文：适用范围 / 编程语言 / 语言版本特性（按需） / 注释风格 / 禁止项 / 正向示例 / 反向示例 / 个性化扩展挂载点
- 内容基底取该语言通用最佳实践，按项目实际情况裁剪；可参考 references/code_rule_examples.md、references/unit_template.md
是否现在创建？也可先只覆盖部分主题（如只做注释风格与命名约定）。
```

**5. 提示纪律**：
- 只提示、不代建；用户拒绝后，同一会话不再重复提示同一语言
- 同一语言仅提示一次，多个缺口在一条消息内合并列出
- 缺口提示仅为建议来源，**不写 memory logs、不触发蒸馏**（与记忆体系独立，见下节）

## Step 8 长度监控与精炼例行（每次触碰 rules 必做）

长度监控不是独立任务，而是**每次触碰 rules 的固定收尾动作**：改前看现状 → 改后做精炼评估，两步都做完才算完成。脚本通过 ≠ 已精炼。

**阈值口径**：

| 字符数（含 frontmatter） | 判定 | 动作 |
|---|---|---|
| ≤7000 | 合规 | 照常收尾，但仍须做一次精炼评估 |
| 7000–8000 | 临近上限（脚本提示） | 必须精炼；确无可压空间则准备拆分方案 |
| >8000 | 不合规（尾部被平台截断） | 立即按 Step 1.1：先精炼 → 仍超则按主题拆分 |

**改前监控**：本次任务会用到编码规范时，先跑 `bash scripts/list_rules.sh` 看长度现状——不先看，可能整场都带着被截断的规则工作。

**改后精炼评估（必做，不因未超限而跳过）**：

1. 跑 `scripts/list_rules.sh`：长度、同文件重复条文、必备单元、客观性
2. 读改动文件全文，按三项扫冗余：① 同文件重复条文、示例与正文重复；② 过程叙述（历史 / 背景 / 讨论 / 变更记录）；③ 长句与形容词堆砌（拆为"判定 + 例外"）
3. 有可压缩项当场精炼，口径见 Step 5 第 7 条：**只压措辞、不压信息**
4. 无可压缩项时，在收尾报告中**明确写出"已评估，无可精炼项"**，不得默不作声跳过
5. 精炼后复跑脚本，并逐条核对判定口径 / 例外 / 禁止项 / 关键示例仍在（不是只看字符数下降）

**报告口径**：涉及 rules 的任务收尾时，按文件给出「精炼前 → 精炼后」字符数与结论；仍 >7000 的说明原因与后续计划。

**禁止**：只跑脚本不看内容（脚本查不出长句冗余）；为降字符数删条款或示例（信息完整性优先，宁可拆分）。

## 与记忆体系协同

修改 rules 与记忆体系相互独立：**无需**记录 memory logs、**无需**触发蒸馏。

- rules 变更只影响 `.codebuddy/rules/` 下的行为约束，不构成项目关键信息（定位/技术栈/架构/关键约定）的变化
- memory 记忆体系（`PROJECT.md`/`PROFILE.md`/logs/`MEMORY.md`）由 `init-mem` 管理，本 skill 不写入、不蒸馏
