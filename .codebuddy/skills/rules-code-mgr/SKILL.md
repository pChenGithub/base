# Rules Code Mgr — 编码类 rules 生成器

## Overview

本 skill 指导 AI 创建、修改、编码 **编码类 rules 文件**（CodeBuddy `.mdc` 规则，位于 `.codebuddy/rules/`）。核心三要素：

1. **文件命名规范**：固定前缀 `code`、按语言分文件、跨语言通用主题独立文件，保证可检索、可排序
2. **内容必须单元**：编程语言、语言版本特性（不强制指定版本，仅按需记录版本差异）、注释风格、禁止项、正向示例、反向示例
3. **个性化扩展挂载点**：每个 rules 预留可自由扩展的模块化单元

> 范围界定：本 skill 只管**编码类型**的 rules（如代码风格、语言规范、禁止项、示例）。**不管理** memory 记忆体系（归 `init-mem`）、rules 加载桥接（`rules/memory_load.mdc`，归官方机制）。

## 工作流决策

开始前先判定任务类型：

- **创建新规则** → 按【Step 0 前置盘点】→【Step 1 拆分与命名】→【Step 2 必备单元】→【Step 3 个性化挂载点】→【Step 4 写入与验证】
- **追加单条规范（目标文件已存在）** → 直接并入现有文件对应小节，按【Step 5 修改流程】
- **修改现有规则** → 按【Step 5 修改流程】（先读现有文件 → 定位单元 → 定向替换 → 校验）
- **编码（规范化）现有规则** → 按【Step 6 编码流程】（将非规范/散落规则纳入命名规范、补齐必备单元）
- **发现语言覆盖缺口（项目使用某语言但 rules 无对应规范）** → 按【Step 7 语言覆盖度检查】提示新建并给出建议（**不擅自新建**）

## Step 0 前置盘点（创建/追加必做）

创建新规则或追加规范前，**必须先盘点** `.codebuddy/rules/` 已有文件：

1. **列出** `.codebuddy/rules/` 全部规则文件
2. **查重**：判断本次需求是否命中已有文件（同语言或同主题）
3. **判定归属**：
   - 已存在对应语言文件 → **并入现有文件**（不新建），按 Step 5 追加小节
   - 已存在对应通用主题文件 → 追加到该通用文件对应小节
   - 不存在对应文件 → 进入 Step 1 新建文件

## Step 1 拆分决策与文件命名规范

### 1.1 拆分决策规则

编码类 rules 按以下规则决定文件粒度：

| 场景 | 拆分方式 | 示例文件 |
|------|----------|----------|
| 同一语言的多主题规范 | **合并为一个文件**（一个语言一个文件） | `code_cpp.mdc`（含 C++ 的版本特性/注释/禁止项/示例） |
| 跨语言通用的主题 | **独立成文件**（如注释风格、命名约定） | `code_comment.mdc`、`code_naming.mdc` |

- 一个语言一个文件，不按主题拆散同一语言
- 只有跨语言通用的规范才独立成文件
- 语言文件与通用文件内容重叠时，通用文件放"通则"，语言文件放"特例"并互相引用

### 1.2 命名格式

```
.codebuddy/rules/code_<语言或通用主题>.mdc
```

| 要素 | 规范 | 示例 |
|------|------|------|
| 前缀 | 固定 `code`，编码类统一，无序号 | `code_` |
| 主体 | 语言名（cpp/c/python）或通用主题（comment/naming） | `code_cpp.mdc`、`code_comment.mdc` |
| 后缀 | `.mdc` | - |

**命名硬性要求：**
- 所有编码类 rules 以固定前缀 `code_` 开头（**不使用序号**），便于 `ls`/搜索一次性检索
- 主体小写 + 下划线，单词式，表意清晰
- 禁止使用含空格、中文、大写驼峰的文件名
- 记忆加载桥接 `memory_load.mdc` 保留原名，不属于编码类（本 skill 不管理）

### 1.3 文件名确定流程

文件名由"归属判定 → 查重 → 主体词定名"三步推导（不是凭空取名）：

**Step A 判定归属类型**（决定主体词是语言名还是主题词）：
- 规则只适用于**单一语言** → 语言文件，主体 = 语言名
- 规则适用于**多种/所有语言** → 通用主题文件，主体 = 通用主题词

**Step B 查重**（结合 Step 0 盘点）：
- 已有同语言文件（如 `code_cpp.mdc`）→ **并入现有文件**，文件名不变，不新建
- 已有同主题文件（如 `code_comment.mdc`）→ 并入
- 无对应文件 → 新建，进入 Step C

**Step C 生成文件名并校验**：
- 格式 `code_<主体>.mdc`；主体词小写 + 下划线
- 语言名用约定俗成缩写（`c`/`cpp`/`python`）；通用主题词用表意清晰的名词（`comment`/`naming`/`error_handling`）
- 校验：无空格/中文/大写驼峰/序号；主体词不与语言名混淆

| 需求 | 判定 | 文件名 |
|------|------|--------|
| C++ 编码规范 | 单语言 → `cpp` | `code_cpp.mdc` |
| 所有语言注释规范 | 跨语言 → `comment` | `code_comment.mdc` |
| C++ 禁止裸指针 | 单语言 + 已有文件 | **并入** `code_cpp.mdc`，不新建 |

## Step 2 内容必须单元

每个编码类 rules 文件**必须**包含以下单元（缺失即为不合规）：

### 2.1 frontmatter（必填）

```yaml
---
description: 一句话说明规则适用范围与触发场景
globs:            # 适用的文件匹配模式，不限定则省略
---
```

### 2.2 正文必备单元

按顺序组织：

| 单元 | 内容 | 必填 |
|------|------|------|
| 适用范围 | 适用的语言/项目/文件类型 | 是 |
| 编程语言 | 目标语言（如 C++ / Python） | 是 |
| 语言版本特性 | 不强制指定版本；仅记录影响编码的版本差异，AI 已知的通用特性不赘述 | 否（按需） |
| 注释风格 | 注释的格式要求（文件头/函数头/行内，语言/中文） | 是 |
| 禁止项 | 明确不允许的行为/写法（负面约束） | 是 |
| 正向示例 | 符合规范的代码示例（`// 正确`） | 是 |
| 反向示例 | 违反规范的代码示例（`// 错误`） | 是 |
| 个性化挂载点 | 见 Step 3 | 是 |

## Step 3 个性化扩展挂载点

每个 rules 文件尾部预留一个**可自由扩展的模块化单元**，供后续按项目/用户习惯追加内容：

```markdown
## 个性化扩展

> 本单元为扩展挂载点：可根据项目/用户需要自由追加模块化小节，不破坏既有结构。
> 追加时保持小节独立、命名清晰、编号递增（## 个性化扩展 1、## 个性化扩展 2 …）。

### 个性化扩展 1
<!-- 追加内容：例如项目专属命名约定、团队特定规范、工具链约定等 -->
```

**规则：**
- 挂载点必须存在且格式固定（保留引导注释）
- 追加内容不得改动前面的必备单元；新增小节编号递增
- 若无扩展内容，保留空挂载点即可

## Step 4 创建流程（完整示例）

**内容基底**：规范条目以**通用最佳实践**为基底（如 Google C++ Style 精简版等），按项目实际情况裁剪；用户明确口述强调的规范优先、必须收录。

**写入方式**：直接按流程生成完整 `.mdc` 并落盘（无需先征求确认），结果供用户检查。

以"创建 C++ 编码规则"为例：

```text
code_cpp.mdc
```

```markdown
---
description: C++ 编码规范规则：语言版本特性、注释风格、禁止项与正反示例
globs: "**/*.{cpp,h,hpp,cc}"
---

# C++ 编码规范

## 适用范围

适用于本项目所有 C++ 源码（.cpp/.h/.hpp/.cc）。

## 编程语言

- 语言：C++
- 语言版本特性：项目编译选项 `-std=c++0x`（C++11）；C++11 通用特性（智能指针/auto/lambda）AI 已知，不赘述

## 注释风格

- 文件头：标明文件用途、作者、创建日期
- 函数头：`/** @brief 功能说明 @param 入参 @return 返回值 */`
- 行内注释：中文，`//` 单行，解释"为什么"而非"是什么"

## 禁止项

- 禁止使用 `using namespace std;`（全局污染）
- 禁止在头文件中定义非 inline 全局对象
- 禁止魔法数字裸用

## 正向示例

```cpp
// 正确：局部使用 using 声明 + 具名常量
void openDoor(int doorId) {
    const int kMaxDoors = 8;
    if (doorId >= 0 && doorId < kMaxDoors) {
        relayOn(doorId);
    }
}
```

## 反向示例

```cpp
// 错误：using namespace + 魔法数字
using namespace std;
void openDoor(int a) {
    if (a >= 0 && a < 8) { relayOn(a); }
}
```

## 个性化扩展

> 本单元为扩展挂载点：可根据项目/用户需要自由追加模块化小节，不破坏既有结构。
> 追加时保持小节独立、命名清晰、编号递增（## 个性化扩展 1、## 个性化扩展 2 …）。

### 个性化扩展 1
<!-- 追加内容：例如本项目（ZYACS_Dctr_328）约定：底层 C 实现 + 上层 C++ 封装，extern "C" 混编 -->
```

**创建完成后：** 运行 `scripts/list_rules.sh` 验证命名与结构合规。

## Step 5 修改流程

1. **先读**：读取目标 rules 完整内容（不要凭记忆猜测）
2. **定位**：确定要改的单元（必备单元 or 个性化扩展）
3. **定向替换**：用 `replace_in_file` 精确替换目标单元，保持其余结构不动
4. **校验**：确认必备单元仍在、`code_` 前缀与文件主体未变、示例与正文一致

**追加单条规范（并入现有文件）**：经 Step 0 判定目标文件已存在时，将新规范写入对应主题小节——新增禁止项/示例则追加进对应列表；新增主题则新增小节并保持单元顺序；不新建文件。

## Step 6 编码流程（规范化既有规则）

1. **盘点**：列出 `.codebuddy/rules/` 下全部文件，识别命名不合规（缺 `code_` 前缀、非规范命名）的文件
2. **重命名**：按 Step 1 规范统一（编码类加 `code_` 前缀；同语言拆散文件先按 1.1 合并；保持原内容）
3. **补齐**：检查每个文件必备单元，缺失的按 Step 2 补齐；已有内容不重复
4. **挂载点**：确保尾部存在个性化扩展挂载点
5. **验证**：运行 `scripts/list_rules.sh` 检查
6. **登记**：在变更说明中列出 文件 → 变更项

## Step 7 语言覆盖度检查（主动提示）

在编码、改码、评审、接手项目等任务中，若识别出项目实际使用的编码语言，须核对其在 `.codebuddy/rules/` 是否有对应的语言规范，避免"无规范可依"。

**1. 识别项目语言**：按源码扩展名与构建/工程文件判定（`*.c/*.h`→C，`*.cpp/*.cc/*.hpp`→C++，`*.py`→Python，`*.js/*.ts`→JS/TS，`*.java`→Java，`*.go`→Go，`*.rs`→Rust，`*.sh`→Shell；`CMakeLists.txt`/`*.pro`/`Makefile` 等仅作辅助，不单独作为语言依据）。

- **判定范围**：只统计**项目自研源码**（含构建脚本）；**排除第三方/依赖目录**（如 `base/` 或 `third_party/`、`vendor/` 下的库自带脚本），避免把依赖包里的 `.py`/`.sh` 误判为项目语言而产生误报
- **证据要求**：提示缺口时须给出依据（命中的扩展名与所在目录），便于用户核对

**2. 期望文件名对照**（主体词取约定俗成缩写，命名规则详见 `references/naming_convention.md`）：

| 语言 | 期望文件 |
|------|----------|
| C | `code_c.mdc` |
| C++ | `code_cpp.mdc` |
| Python | `code_python.mdc` |
| Shell/Bash | `code_shell.mdc` |
| JavaScript / TypeScript | `code_js.mdc` / `code_ts.mdc` |
| Java | `code_java.mdc` |
| Go | `code_go.mdc` |
| Rust | `code_rust.mdc` |
| 其他语言 | `code_<语言缩写>.mdc` |

**3. 判定与处理**：
- 已有对应文件 → 无缺口，不提示
- 无对应文件 → **缺口**：**不擅自新建**，向用户提示并给出建议；用户确认后按 Step 1~4 创建
- 只缺"跨语言通用主题"（如注释风格）时不单独报缺口，作为可选建议附带提出

**4. 提示模板**（缺口时一次列清，避免反复打断）：

```text
发现项目使用 <语言>（依据：<源码扩展名 / 工程文件>），但 .codebuddy/rules/ 下没有对应的编码规范文件。
建议新建 <期望文件名>，按本 skill 必备单元组织：
- frontmatter：description + globs（如 "**/*.{<扩展名>}"）
- 正文：适用范围 / 编程语言 / 语言版本特性（按需） / 注释风格 / 禁止项 / 正向示例 / 反向示例 / 个性化扩展挂载点
- 内容基底取该语言通用最佳实践，按项目实际情况裁剪；可参考 references/code_rule_examples.md、references/unit_template.md
是否现在创建？也可先只覆盖部分主题（如只做注释风格与命名约定）。
```

**5. 提示纪律**：
- 只提示、不代建；用户拒绝后，同一会话不再重复提示同一语言
- 同一语言仅提示一次，多个缺口在一条消息内合并列出
- 缺口提示仅为建议来源，**不写 memory logs、不触发蒸馏**（与记忆体系独立，见下节）

## 与记忆体系协同

修改 rules 与记忆体系相互独立：**无需**记录 memory logs、**无需**触发蒸馏。

- rules 变更只影响 `.codebuddy/rules/` 下的行为约束，不构成项目关键信息（定位/技术栈/架构/关键约定）的变化
- memory 记忆体系（`PROJECT.md`/`PROFILE.md`/logs/`MEMORY.md`）由 `init-mem` 管理，本 skill 不写入、不蒸馏

## 校验清单（每任务必过）

- [ ] 创建/追加前已盘点 `.codebuddy/rules/` 并判定归属（已存在则并入，不重复建文件）
- [ ] 文件命名符合 `code_<语言|通用主题>.mdc`（固定前缀 `code`、无序号、主体小写下划线）
- [ ] 拆分符合 1.1：一个语言一个文件；仅跨语言通用主题独立成文件
- [ ] frontmatter 含 description（有匹配时含 globs）
- [ ] 必备单元齐全：适用范围/语言/版本特性（按需）/注释风格/禁止项/正反示例
- [ ] 个性化扩展挂载点存在且格式固定
- [ ] 正反向示例与禁止项、规范一一对应（示例支撑约束）
- [ ] 修改未破坏既有单元结构与 `code_` 前缀命名
- [ ] 修改 rules 不写入 memory logs、不触发蒸馏（与记忆体系独立，由 `init-mem` 管理）
- [ ] 识别到项目所用语言在 rules 无对应规范时，已提示用户并给出新建建议（**未擅自新建**）
