# Proto Archive（协议采集与归档）

## Overview

把**已定义好的协议**从任意载体（网页 / Word / Markdown / PDF / 文本 / 代码注释）中完整、准确地提取出来并结构化归档。归档必须弄清三件事：**① 请求/发起方式、② 发送内容、③ 接收/响应内容**，逐条产出字段表，按 init-mem 规范写入当前项目的记忆扩展文件，供开发与联调直接引用。

本 skill **不做协议设计**，只忠实归档已有协议；歧义与缺失标注"待确认"并向用户澄清，不臆测补全。

**与 init-mem 的关系**：归档落点 `memory/pro_<简称>/PROJECT_<主题>.md`（默认主题"协议"）属于 init-mem 记忆体系的"项目描述扩展文件"。本 skill 负责**协议采集与条目结构化**；扩展文件的命名、内容格式、蒸馏刷新按 init-mem 规范执行（创建扩展文件前须与用户确认主题后缀）。

## Workflow

### Step 1 明确目标与当前项目
- 确认本次归档对象：单个协议还是多个？类型（HTTP/MQTT/二进制/其他）？
- 判定当前操作项目（沿用 init-mem 规则：memory/ 下仅一个项目文件夹时默认其为当前操作项目）
- 目标文件默认 `memory/pro_<简称>/PROJECT_协议.md`（多协议混合归档）；文件不存在且需新建时，**先与用户确认主题后缀**（默认"协议"）再创建

### Step 2 采集原始定义（多来源）
| 来源 | 采集方式 |
|---|---|
| 网页 | `web_fetch` 抓取页面；`web_search` 检索补充 |
| Word（.docx） | 读取文档内容（含表格/段落） |
| Markdown / 纯文本 | 直接读取文件 |
| PDF | 按需提取文本 |
| 聊天粘贴内容 | 直接采纳 |
| 代码/配置注释 | 搜索源码中协议定义、报文示例、注释说明 |

- 每条采集记录**保留来源与日期**（来源链接 / 文件路径 / 文档名 + 采集日期），便于溯源
- 协议定义常分散于多页 / 多文件 / 多示例：先建立"协议全景"（有哪些消息、由谁发起、完整链路），再逐条提取，避免漏采版本差异与修订说明

### Step 3 理解协议三要素
按协议类型提取核心事实：
- **① 请求/发起方式**：发起方与接收方、触发条件、方向。
  - HTTP：Method + URL/路径 + Header + Query 参数
  - MQTT：Topic（含通配符规则）+ QoS + 发布/订阅方向 + Retain
  - 二进制/自定义帧：帧头、命令字、帧结构、校验方式、交互时序
- **② 发送内容**：报文/载荷的字段结构（字段名 / 类型 / 长度 / 必填 / 取值说明 / 示例）
- **③ 接收/响应内容**：应答与上报的字段结构、成功/失败标志、错误码含义
- 同步/异步、心跳/保活、超时重试等时序约束一并记录
- 歧义或原文缺失处 → 标注"待确认"并询问用户，不擅自编造

### Step 4 结构化归档
- 按 `references/protocol_template.md` 的条目模板逐协议归档到目标扩展文件
- 文件已存在：追加新条目或**更新既有条目**（不重复登记，更新处标注日期）
- 二进制协议必须给出**字节偏移布局表**；数值注意大小端与编码方式（hex/BCD/ASCII）
- 条目头部更新"更新日期"；归档完成后按 init-mem 维护流程处理（一般性变更在 MEMORY.md 顶部标记 `⚠ 需重新蒸馏`，关键约定变化实时蒸馏）

### Step 5 汇报
向用户汇报：
- 已归档的协议清单（类型 / 条数 / 落点文件）
- 每条的关键结论摘要（请求方式 → 发送要点 → 响应要点）
- 待确认项清单（歧义 / 缺失 / 需要用户补充的定义）

## 结构化要求

- 每条协议一个二级标题条目，**必含**：定位、请求/发起方式、发送内容、接收/响应内容；错误码与时序约束有则必录
- 字段一律用**表格**呈现（模板见 references），表格优于自由文本
- 保留原文出处引用，便于与协议文档对照复核

## Resources

- `references/protocol_template.md`：协议条目统一模板（HTTP / MQTT / 二进制三类字段表与字节布局表示例）、PROJECT_协议.md 章节组织示例。归档时**必须加载并对照**。
