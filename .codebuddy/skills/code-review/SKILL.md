# Code Review（代码审查）

## Overview

对代码做两件事，缺一不可：

1. **规范符合性核对**：代码是否符合项目编码规范。
2. **主动问题发现**：规范之外，主动排查缺陷与风险（内存/资源/并发/边界/错误处理/可移植性/逻辑/接口兼容）并**提醒**。

走查产出**精炼异常清单**；**默认只审查、不修改代码**。用户确认清单并指定编号后，按 `references/逐条处理流程.md` **逐条给出方案与代码、逐条确认、逐条修改**（铁律：未经逐条确认不得改代码；不得改动既有对外接口）。

- 规范符合性标准：**只引用** `.codebuddy/rules/code_general.mdc`（通用）、`code_c.mdc`（C）、`code_cpp.mdc`（C++）——**不另立标准、不复制规则正文**；冲突以规则原文为准。
- 问题发现标准：`references/问题模式库.md`（C/C++ 高危模式库）。
- **触发词（用户这样说即调用本 skill）**：审查代码 / code review / 代码检查 / 检查编码规范 / 检查代码问题 / 提交前自检 / 看看这段代码有没有问题 / 帮我 review 一下 / 处理异常 / 逐条修复 / 修复审查发现的问题。

## 边界（与其它组件各自独立、互不交叉引用）

| 组件 | 职责 |
|---|---|
| `.codebuddy/rules/code_*.mdc` | 规范**本体**（会话常驻加载的硬约束） |
| 本 skill | 按规范**审查代码** + **主动发现问题** + 出报告（只读） |
| `rules-code-mgr` | 生成/维护**规则文件**（不审代码） |
| `req-check` | 检查**需求与项目描述**（不审代码） |

## Workflow

### Step 1 界定审查范围

- 明确审查对象：指定文件/目录、或本次 `git diff` 改动。
- **未指定时先询问范围**，不擅自全仓扫描；范围过大时建议分批。
- 记录范围清单（文件 + 行数）与审查依据，作为报告头部。
- 范围无法访问或不存在 → 报告并停止，不臆造结论。

### Step 2 规范符合性检查

加载 `references/规范检查清单.md`（其条目已逐条映射到 `code_*.mdc`），按 A~F 类逐项核对：

- A 注释：变量/成员/宏/函数 JSDoc（`@brief`/`@param`/`@return`）、注释位置（`.h` vs 实现）、C 用 `/* */`
- B 命名：函数/变量/宏/typedef/成员/文件命名、include guard 宏名
- C 结构：include guard、include 顺序、C89 声明位置、C++ 声明与实现分离、`extern "C"`
- D 逻辑与接口：下标从 0（禁 `<=`）、定义即初始化、数组带长度、复杂数据指针传参、指针判空、返回值类型、函数长度、栈上 1024 字节限制、错误码为正数
- E 错误处理与日志：错误分支必打日志、提前退出、`goto` 限错误清理、`LOG_*` 规范与 `lib_log_init()` 顺序
- F 禁止项：逐条核对禁止项对照表

命中项记录：**规则文件 + 小节名 + 条目号**（如 `code_c.mdc「禁止项」`）。

### Step 3 主动问题发现（规范之外）

加载 `references/问题模式库.md`，按 8 类主动排查：内存 / 资源 / 并发 / 边界与类型 / 错误处理 / 逻辑 / 嵌入式特有 / 接口兼容。

- 重点排查规范**不覆盖**但会造成故障的问题：泄漏、double free、越界、竞态、死锁、整数截断、格式串不匹配、32/64 位差异、`volatile` 缺失、接口被改动等。
- **辅助线索**：可执行 `sh scripts/scan_risky_patterns.sh <路径> [扩展名...]` 快速定位可直接检出的禁止项（`strcpy`/`#pragma once`/`goto`/`scanf`/裸 `new` 等）与高危调用；脚本输出**只是线索，不是结论**。
- 脚本命中项须逐条回代码上下文复核后才计入报告。

### Step 4 分级与判定

加载 `references/报告模板.md` 的定级标准定级：

- 🔴 阻断 / 🟠 严重 / 🟡 建议 / 🔵 风格。
- 每条必须给出**依据**：规则条目号，或问题模式库编号，或完整推理链。
- **证据不足的只写"疑似"并列出待确认点**，不臆断、不夸大。
- **涉及第三方库 / 系统 API 行为的结论**（是否崩溃、是否复制参数/字符串、NULL 是否安全、返回值语义等）**必须先核实**（本地源码 / 官方文档 / 可复现实验），并把核实来源写入"依据"；**禁止凭记忆断言**。
- 同一问题若同时属规范违规与缺陷，取**更严级别**合并只报一次。

### Step 5 输出精炼异常清单并等待确认

**先输出「精炼异常清单」，不直接改代码、不展开长报告。** 格式见 `references/报告模板.md`「精炼异常清单」：每条一行，仅含 `编号 / 级别 / 位置 / 问题（一句话）/ 影响`。

- 清单**只描述事实**，**不给修复方案、不给代码**。
- 细节（证据、推导、规范符合性汇总）仅在用户追问时展开；需长文时按 `references/报告模板.md` 出详细报告或落盘（路径需用户确认）。
- 输出后请用户确认**要处理哪些编号**；未获确认**不得修改任何代码**。

### Step 6 逐条确认后修改（用户指定编号后）

加载 `references/逐条处理流程.md`，**一次一条**，每条都必须停下等确认：

1. 给出三段式说明：**问题点**（位置 + 原码证据 + 触发条件/影响）→ **修复方案**（改哪里；A 内部修复 / B 新增接口 / C 挂起；风险）→ **代码修改内容**（原码 → 新码对照）；
2. **停下等用户确认**（确认 / 调整 / 跳过 / 挂起）；
3. 确认后才修改；**不得合并确认、不得越界改无关代码**；
4. 立即编译/语法验证；
5. 逐条回执，然后进入下一条。

- **铁律**：不得改动既有对外接口（函数签名 / 结构体字段 / 枚举与宏 / 文件名）——遵循项目原则①「接口不修改，只能添加」。
- 改写的代码**当场合规**（JSDoc、变量注释、`/* */`、错误分支 `LOG_E`），禁止"跟随存量风格"。
- 挂起项与未处理项**必须显式列出**。

## 纪律

- **未经用户逐条确认，不得修改任何代码**——即使问题明显、改动很小，也须先出方案等确认；处理按 `references/逐条处理流程.md` 执行；不改规范文件（规范调整属 `rules-code-mgr`）。
- 每条问题必须有位置与依据；无依据不列。
- 有结论、有理由据；不与用户已有的存量风格偏好混淆——规则优先于存量代码风格。
