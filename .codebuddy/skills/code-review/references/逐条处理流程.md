# 修复流程（两阶段：清单确认 → 逐条确认）

> 触发：走查完成，或用户说"处理 / 修复 / 逐条处理"。
> **铁律：任何代码修改都必须先获用户逐条确认。未确认不得改——哪怕问题明显、改动很小。**

## 阶段一：走查 → 精炼异常清单（只列问题，不给方案）

- 走查完成后**先输出「精炼异常清单」**，**不直接改代码、不展开长报告**。
- 清单每条一行，**只描述事实**（问题 / 位置 / 后果），**不写修复方案、不给代码**：

| 编号 | 级别 | 位置 | 问题（一句话） | 影响 |
|---|---|---|---|---|
| C-01 | 🔴 | `curl/ifaceHttpReq.c:76` | 空指针检查分支内仍解引用 `reply` | 触发即崩溃 |

- 编号规则：`<模块代号>-<序号>`（C=curl、Z=zyEcp、S=string、F=file、T=timeopt、L=linkedList…）。
- 细节（证据、推导、规范符合性汇总）**仅在用户追问时展开**；需要长文时另出详细报告（见 `报告模板.md`），落盘路径需用户确认。
- 清单输出后，用一句话请用户确认：**要处理哪些编号**。

## 阶段二：逐条确认 → 修改（一次一条）

用户指定编号后，**逐条**执行以下循环，**每条都必须停下等确认**：

1. **给出该条三段式说明（不落笔改代码）**：
   - **问题点**：位置（`文件:行`）+ 原码证据 + 为什么是问题 + 触发条件与影响；
     凡涉及**第三方库 / 系统 API 行为**（崩溃与否、是否复制参数、NULL 语义、返回值含义）**须先核实并注明来源**（源码 / 官方文档 / 实测），**禁止凭记忆断言**；
   - **修复方案**：怎么改、动哪些函数/文件、是否触及对外接口（**A 内部修复 / B 新增接口 / C 挂起**）、风险与副作用；
   - **代码修改内容**：**原码 → 新码**对照（等价 diff），含新增的注释与日志。
2. **停下，等用户确认**（确认 / 调整 / 跳过 / 挂起）。
3. 用户确认后**才**执行修改。
4. 立即编译/语法验证（见第 4 节）。
5. **逐条回执**（见第 5 节），然后进入下一条。

### 铁律与约束

- **不得合并确认**：不得一次抛多条方案后连续改；始终"一条 → 确认 → 改 → 回执 → 下一条"。
- **不得越界**：只改当条涉及的代码，不顺手重构、不顺手格式化、不改无关行。
- **不得改动既有对外接口**（项目原则①「接口不修改，只能添加」）：需要改接口的归 **B（新增接口）** 或 **C（挂起）**，并在方案中显式说明。
- 用户"跳过"的条目不再追问；用户"挂起"的记入挂起清单。

## 三、同错多副本

同一缺陷存在于多份副本时，在方案中提示"**共 N 处**"，用户确认后按**同一修法一并处理**（避免修一漏一）。若重复量已使修改困难，先提议"消除重复"，且属重构，需单独确认。

## 四、改写代码的即时规范（P0）

新写/改写的每一行必须**当场合规**，禁止"跟随存量风格"：

- 变量在函数**开头**声明、**定义即初始化**、逐个加用途注释；
- 新增/改写函数加 `/** @brief @param @return */` 文档注释；
- C 用 `/* */` 注释（禁 `//`）；
- 错误分支**必打 `LOG_E`**（含错误码/原因），正常流程零嵌套；
- 无魔法数字（局部数组长度直接用字面量，属规则例外）；下标仍从 0 开始。

## 五、验证（每条改完必做）

- 本项目无顶层 `.pro`，且**缺宿主 `global.h`** → 临时桩头文件（放 `/tmp`，**不入库**）+ 语法检查：
  `clang -fsyntax-only -Wall -I /tmp/<桩目录> -I <第三方头路径> <源文件>`
- 本机无 `gcc`，用 `cc` / `clang`；**零错误**才算通过。
- 连续 3 次失败即停下请示，不硬闯。

## 六、逐条回执格式

```
[C-01] 已修改
- 变更点：`<文件>:<函数或行>` → <改了什么>
- 依据：<规则条目 / 问题模式库编号>
- 验证：clang -fsyntax-only 通过（零错误）
- 下一条待确认：C-02
```

## 七、收尾

- 全部处理完给出统计：已修 N / 新增接口 M / 挂起 K / 未处理 L。
- **挂起项与未处理项必须显式列出**，不得默认"已全部处理"。
