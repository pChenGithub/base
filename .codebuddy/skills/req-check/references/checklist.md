# Req Check 检查清单（固定）

检查对象：`memory/pro_<简称>/PROJECT.md`（init-mem 项目描述文件）。执行检查时必须逐项对照本清单。

## A. 结构完整性（描述文件是否合规）

- [ ] 元信息齐全：标题（`# 项目名`）、`- 更新日期`、`- 状态`
- [ ] 章节齐全：
  - 项目概述（定位/背景）
  - 技术栈（语言/框架/工具）
  - 软件架构（分层/模块划分/依赖）
  - 项目模块（每个模块：职责 + 主要功能）
  - 启动流程（构建/运行步骤）
  - 备注（可选项）
- [ ] 架构以**树形结构展示项目目录**：软件架构章节用目录树呈现工程结构，逐层标注模块职责与关键文件；层级、目录/文件命名与实际工程一致（非概念框图、非仅职责表格），可「按树即定位代码」
- [ ] 各章节为实质内容，无空泛/占位表述，描述自洽无矛盾

## B. 需求明确性（需求是否明确可执行）

- [ ] 可执行：需求能直接指导开发（有明确对象、动作、边界）
- [ ] 无歧义：无模糊词（如"等""相关""适当"）、无矛盾表述
- [ ] 无空泛：有具体功能点，非口号式描述
- [ ] 优先级/验收标准明确（若适用）

## C. 模块功能澄清（模块功能是否清晰）

- [ ] 每个模块有「职责 + 主要功能」结构
- [ ] 功能描述覆盖输入/处理/输出/异常（或至少列出明确功能点）
- [ ] 模块间边界清晰：无职责重叠、依赖关系明确

## D. 与源码一致性（清单合规 + 源码核对双重）

- [ ] 有源码时：PROJECT.md 模块与工程目录结构一致
- [ ] 功能点与源码实现一致（存在且真实实现）
- [ ] 无源码/不可访问时：跳过并注明「—」

## 澄清提问维度

### 需求澄清
- 范围边界：功能覆盖到什么程度？边界在哪？
- 优先级：哪些是核心/必须，哪些是扩展/可选？
- 验收标准：如何判定需求完成？
- 取舍：需求冲突时的优先级与折中方案？

### 模块功能澄清
- 功能补齐：该模块下是否还缺功能点？
- 输入/输出：输入数据、输出结果是什么？异常如何处理？
- 模块边界：职责是否重叠？与其他模块的依赖关系？
- 未实现项：描述的功能是否已实现/计划实现？
