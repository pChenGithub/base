## 思考方式

- **思考顺序：先整体后局部**——先看全貌，再深入细节
- **决策前准备充分**：查资料验证、找失败案例、列方案对比，想透后再定
- **遇卡顿先停下**：思路卡住时先停下来整理思路再继续，不硬闯
- **架构分析在前，编码在后**：接到需求必须先输出架构分析（涉及哪些层、哪些文件、数据流向），再动手写代码

## 架构与设计偏好

- **模块功能独立**：模块/组件/skill 各司其职、独立自治，不接受职责交叉与相互引用，依赖必须单向；分析设计时先核对职责是否互斥、依赖是否单向（如判定 init-mem 不应引用 req-check：质检标准是验收方的事，生产方引用质检方即耦合）。
- **功能完备**：模块自身能力闭环，不依赖其他模块补齐，不留半成品接口。
- **接口不修改、只能添加**：已对外提供的接口一经确定即不修改，演进只能以**新增接口**方式扩展，保持向后兼容。
- **自底向上构建**：先基础设施再业务页面——store、rules、init 都搭好才写 UI
- **按分层顺序编码**：自底向上，先底层基础设施再上层业务代码，**禁止跳过中间层直接写最终页面**
- **通用代码沉淀基础库、业务极限瘦身**：业务中出现的通用代码沉淀回基础库，持续积累通用能力；业务代码只保留业务本身，尽量做极限瘦身（薄业务、厚基础）。
- **一次性解决，避免来回改**：不喜欢反复修改同一件事——同一问题首次处理时就把机制建好（缓存一次预加载到位、约束规则固化进 skill/rules 自动生效），不留后续反复
- **元层管控**：体系约束分层固化——init-mem skill 管 memory 素材与蒸馏，rules（memory_load 桥接加载 + 编码规范 mdc）管会话加载与代码约束，层层生效、各层自治
- **一次搞清楚**：分析阶段把问题想透，不喜欢编码中途才发现架构问题返工

## 处事方法

- **先堵失败路径再走正常流程**：做事前先考虑规避失败可能，再推进正常流程
- **量力而行**：不承接超出能力/资源范围的工作
- **规则态度**：先执行，发现问题再改规则（不轻易变通既有规则）
- **收尾习惯**：检查验证无误才收尾；完成后复盘总结，形成沉淀
- **最不能容忍**：反复返工、规则被无视

## 代码质量偏好

- **错误优先，提前退出**：写函数先想"有哪些情况会失败"，把所有失败路径堵死后，剩下就是干净的正常流程。错误时立即记录原因并 return/goto 终止，绝不让异常继续传播，正常逻辑零嵌套
- **注释必须详细**：变量和函数必须有注释说明用途，不接受无注释代码
- **类型必须明确**：优先显式声明类型，仅在类型从上下文明显可推断时允许省略（如 `auto` 接收工厂返回值）
- **声明紧凑，实现分隔**：头文件中声明之间不空行（紧凑排布），实现文件中函数之间空一行（逻辑分隔）
- **修改即编译**：每次代码修改完成后，立即执行 x86 编译验证，编译通过才算修改完成
- **编码纪律（编码后严格自查编码规范）**：代码产出/修改后，必须对照项目已固化的编码规范逐项自查再交付——函数/方法 API 注释须 JSDoc 风格（功能说明 + 参数/返回值说明，无参含 Qt 槽函数也须注释）、变量/结构体成员/宏须注释用途、命名与下标从 0 等硬性条目必须遵守；**禁止以"跟随存量代码风格"为由降低规范要求**（编码规范优先于已有代码风格），也禁止用注释为不合规代码"开脱"
